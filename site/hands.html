How to Give an AI Agent Hands in a Real Browser Without Losing a Day to Silent Failures

9 August 2026

Your agent can read the whole internet and cannot click a single button in your own account.

That gap is where most people stop. They wire up a headless browser, discover it knows nothing about them, and go back to copying values out of a dashboard by hand while the agent watches. The work that would actually save time, the invoice that needs importing, the portal that has no API, the report that only exists behind a login, stays manual forever.

The fix is not a better scraper. It is driving the browser you are already signed into, and then handling the four specific failure modes that make everyone who tries it once give up and call browser automation unreliable.

This is the complete build. By the end you will know the architecture, the three commands that carry most of the weight, and the exact silent failure that costs people an entire day, including how to prove it is happening rather than guess.

Why A Fresh Browser Is The Wrong Answer

The obvious approach is to launch a clean browser and drive that. Playwright, Puppeteer, any of them. It works beautifully in a demo and fails on everything that matters.

A fresh browser has no cookies, no session, no device trust. So the first thing your automation meets is a login form, and behind that a second factor, and behind that a device verification email. You now have a system that needs your password stored somewhere, your one-time codes intercepted somehow, and a fingerprint that most banks and government portals will flag on sight.

You have not automated the task. You have built a machine that has to defeat your own security to do the task, and every one of those defeats is a thing that breaks silently the next time the provider changes something.

The alternative is to stop trying to become you and simply borrow the session where you already are you. A browser started with a remote debugging port exposes a control channel. Your agent attaches to that channel and acts inside a session that is already authenticated, already trusted, already past every factor.

No credentials in config. No codes to intercept. Nothing to defeat.

The Shape Of A Safe Setup

That control channel has no authentication of any kind. Anything running as your user can connect to it and act as you everywhere you are signed in. This is not a reason to avoid the approach. It is a reason to be deliberate about four things.

A separate browser profile. Not your daily browser. A profile you sign into deliberately, for the accounts this agent is allowed to touch, so the blast radius is a decision rather than an accident.

A random port every time, bound to loopback only. A fixed, well known port is an invitation. A random port on 127.0.0.1 is not reachable from the network at all.

An explicit close. The channel should be something you open for a task and close when it is done, not a daemon that lives forever because it was convenient once.

A timer you cannot forget. The failure mode is not malice, it is walking away. Start it with a lifetime and let it shut itself down.

start 90        random port, closes itself after 90 minutes
open <url>
...
stop            closes the port. Do this.

If you take nothing else from this piece: an open control port is an open bank window. Treat closing it as part of the task, not as cleanup.

Wait For State, Not For Time

The single highest leverage habit in browser automation, and the one most people skip because a sleep is easier to type.

Every fixed delay in a script is a race waiting to be lost. Too short and it breaks on a slow morning. Too long and every run pays for the worst case. Worse, when it does break, it breaks intermittently, which sends you looking for a bug in your logic when the actual problem is that the page needed 300 more milliseconds.

wait "Receipt"
found after 412 ms

Poll for the condition instead. Wait for the text that proves the page reached the state you need, and let it tell you how long it took. When something genuinely hangs, you get a timeout with a clear message rather than a script that continued into a page that was not ready.

Use it after every action that changes the page. Not sometimes. Every one.

There Are Two Ways To Click And No Rule About Which Works

This is where most people conclude that browser automation is flaky.

A DOM click calls the element's own click method. It is cheap, it works through the page's own event system, and it works on most modern web applications.

A real mouse click scrolls the element into view, reads its position, and dispatches actual mouse events through the browser's input layer, the same path a physical mouse takes.

Neither one is correct. They fail in opposite directions, and you cannot predict which you will need.

An old government portal built on server rendered forms ignored DOM clicks completely and required real mouse events. A modern accounting application did the exact opposite: real mouse clicks on verified correct coordinates did nothing, while a DOM click on the same element worked instantly.

So build both, try the cheap one first, and fall back. If neither works, the element is probably inside a sandboxed frame that JavaScript cannot reach at all, and you need to click a raw coordinate, which goes through the input layer and lands in any frame.

The reason to internalise this is that the failure gives you nothing. The click reports success. The page does nothing. If you have only implemented one method, you will spend that time looking for the bug in your selector.

The Silent Failure That Costs A Day

This is the part worth the whole article, because it is invisible and it looks exactly like your own bug.

Chrome silently drops synthetic mouse clicks into a page it considers unfocused.

Your terminal has the operating system focus, not the browser. On a freshly opened window the renderer still treats the page as focused, so your first click lands. After the first navigation the renderer re-evaluates, decides the page is not focused, and stops delivering synthetic mouse input.

No error is raised. Not from the protocol, not from the browser, not in the console. The call resolves successfully. No listener fires. The click reports a coordinate you can independently verify is dead centre on the button.

The asymmetry is what makes it so expensive. The first click of a session works. So when later clicks stop landing, it does not read as a browser behaviour, it reads as a race condition in your own code, and you go looking in exactly the wrong place.

I verified the coordinates three separate times before accepting they had been right the whole way through. Iframe offset, device pixel ratio, scroll position, page versus viewport coordinates. All measured. All already correct.

What broke the deadlock was refusing to keep guessing and running the same click in a loop, changing exactly one variable per iteration:

navigate, click                    -> works
navigate, click                    -> nothing
navigate, wait 4s, click           -> nothing
navigate, evaluate something, click -> nothing
navigate, click twice              -> nothing

Only the first attempt after browser start worked, and clicking the top level document failed the same way as clicking inside the frame. Not the iframe. Not timing. Not coordinates. Something changed state at the first navigation and never changed back.

Here is what does not fix it:

Page.bringToFront                        no change
Input.setIgnoreInputEvents ignore:false  no change
waiting longer                           no change
clicking twice                           no change

Here is what does:

await send('Emulation.setFocusEmulationEnabled', { enabled: true });

Send it once when you attach. The effect lasts the session, so every later click is covered by that single call.

There is one more detail that explains why this survives so long in a codebase. It only reproduces while the browser window is unfocused. The moment you click into the window to watch it happen, it stops happening. A bug that hides while you observe it is how one line costs a day.

Where The Page Hides From You

Two structures will make a page look empty or unclickable when it is neither.

Iframes. Many business applications render their entire interface inside a frame. Reading the page text works, because text extraction can walk into a same origin frame. Clicking does not, because your selector is running against the top document where the button does not exist. You need to target the frame's document explicitly. Cross origin frames cannot be reached from JavaScript at all, which is worth detecting up front so you stop trying.

Shadow DOM. Portals built from web components return almost nothing from the top level text. One government portal returned the single phrase "Start of e-service" while displaying a complete form on screen. Your extraction has to walk through shadow roots deliberately, or you will conclude the page failed to load.

The practical rule: when a page looks empty but clearly is not, take a screenshot before you trust any text you extracted. The screenshot is ground truth. The text is an interpretation.

One More Trap, Because It Is The Expensive Kind

Uploading a file is not submitting it.

Both authorities I tested against accept a file, show a confirmation for the transfer, and then wait for a separate signature before anything is actually filed. A workflow that ends when the upload succeeds has submitted nothing at all, while reporting complete success.

Read the confirmation text. Look for a second step. This is the failure mode that does not surface until a deadline has passed.

While we are here: filenames can matter more than you expect. One upload required two files where the first contained a line naming the second by exact filename. Renaming either one failed with no useful error.

Test It Before You Trust It

Run these deliberately before you point any of this at something that matters. Most setups that fail in real use would have failed one of these immediately.

The unfocused test. Run your clicks with the browser window visible but not focused, which is how it will always run in practice. If you only ever tested with the window focused, you have not tested the thing described above.

The second navigation test. Navigate, act, navigate again, act again. A surprising number of failures only appear on the second cycle, because the first one runs against fresh state.

The empty page test. Point your text extraction at a page built from web components. If it returns almost nothing while the screenshot shows a full interface, your extraction is not walking shadow roots.

The wrong element test. Search for text that appears on several elements. Does your click pick a sensible one, or the first one in document order that happens to be an invisible container.

The did-it-actually-submit test. After any upload or form submission, assert on the confirmation the service gives you, not on the fact that your own command returned successfully.
