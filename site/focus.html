Chrome silently drops synthetic mouse clicks into unfocused pages

9 August 2026

If you drive Chrome over the DevTools Protocol and dispatch real mouse events, there is a failure mode waiting for you that produces no error anywhere. Not from CDP. Not from Chrome. Not in the console. Your code reports a successful click at coordinates you can prove are correct, and the page does not react.

The first click of a browser session works. Every click after the first navigation is swallowed. That asymmetry is what makes it expensive: it does not look like a browser behaviour, it looks like a race condition in your own code.

The symptom

We were clicking a button inside a same-origin iframe. The command reported success:

clicked "Transfer amount" (1 match, real mouse click at 98,378)

The button's centre, measured in the page at that moment, was at 97,377. One pixel of rounding. The element was visible, in the viewport, not covered, and document.elementFromPoint at that exact coordinate returned the button itself. Everything checked out. Nothing happened.

Three wrong hypotheses

The obvious suspect is coordinates, especially with an iframe involved, so we went there first and stayed too long. Iframe offset. Device pixel ratio. Scroll position. Page coordinates versus viewport coordinates. We measured each one and each one was already right.

The thing that broke the deadlock was refusing to keep guessing and instead running the same click in a loop while changing one variable at a time:

1  navigate, click  ->  works
2  navigate, click  ->  nothing
3  navigate, wait 4s, click  ->  nothing
4  navigate, evaluate something, click  ->  nothing
5  navigate, click twice  ->  nothing

Only the very first attempt after the browser started worked, and clicking the top document instead of the iframe failed the same way. So it was not the iframe, not timing, and not coordinates. Something changed state at the first navigation and never changed back.

What it actually is

The browser window does not have operating system focus. Your terminal does. On a fresh window the renderer still treats the page as focused, which is why the first click lands. After a navigation the renderer re-evaluates, concludes the page is not focused, and quietly stops delivering synthetic mouse input.

Quietly is the important word. Input.dispatchMouseEvent resolves successfully. There is no exception, no protocol error, no console warning, and no event listener fires.

What does not fix it

AttemptResult
Page.bringToFrontno change
Input.setIgnoreInputEvents with ignore: falseno change
Waiting longer before the clickno change
Clicking twiceno change
Emulation.setFocusEmulationEnabledfixed

The fix

await send('Emulation.setFocusEmulationEnabled', { enabled: true });

Send it when you attach to the target. The effect lasts for the session, so one call at connection time covers every later click. In our tests the very next trial passed without re-applying it.

If you are writing your own CDP automation and your synthetic clicks are intermittently doing nothing, this is almost certainly why, and you are probably about to spend an afternoon measuring coordinates that were correct from the start.

Reproducing it

You need a page with a button, a browser started with --remote-debugging-port, and a terminal that has focus while you run it. Attach, then:

navigate  ->  click by dispatched mouse events  ->  assert the handler ran
navigate  ->  click again        ->  the assert fails

Keep the browser window visible but unfocused. If you click into the browser window with your actual mouse first, the bug disappears, which is another reason it survives so long in a codebase: it does not reproduce while you are watching it closely.

Why this is worth writing down

Every agent that drives a real browser hits this eventually, because agents run from a terminal and the browser is never the focused window. The failure is silent, asymmetric and looks like your own bug, which is the worst combination a bug can have.

It is one line. It cost us a day.
